**Estado: OPEN (preregistrado)** — primer gate de producto, no de
investigación. Abre tras el cierre definitivo de la línea de extracción
automática: `g0-final-fail`, `g1-final-fail`, `g2-a-final-fail`,
`g2-b-final-fail` (commits `82aec58`…`ccb1770`).

## 0. Cierre de la línea de investigación

```text
G0  FAIL   baseline determinista insuficiente sobre holdouts
G1  FAIL   linkage PASS / extraction FAIL (invented=101 con provenance=1.0)

           (ambigüedad irreducible cross-issuer; wc=0 => recall=0)

```

Conclusión científica: la extracción contractual automática **general** no es
alcanzable sin plantillas por emisor. Es una frontera medida, no una
limitación de esfuerzo. Los tags `-final-fail` son activos del proyecto:
justifican experimentalmente por qué el producto es human-in-the-loop.

## 2. Pregunta de P0

> ¿Puede una persona revisar y confirmar los términos de una emisión de forma
> sustancialmente más rápida y segura usando Emisiones ES que leyendo
> manualmente los documentos CNMV?

No es una pregunta de modelo: es una pregunta de **producto operativo**.

## 3. Arquitectura de aceptación

```text
CNMV / ESMA / GLEIF / venues
            │
            ▼
      acquisition
            │
            ▼
   identity + document graph
            │
            ├──────────────► reference data
            │
            ▼
     safe document linkage
            │
            ▼
 candidate term extraction        <- "candidate", nunca hecho canónico
            │
            ▼
     EXACT EVIDENCE (page+bbox+lexeme)
            │
      ┌─────┴─────┐
      ▼           ▼
 CONFIRM        REJECT
      │
      ▼
 reviewed canonical terms
```

Separación invariante:

```text
machine_candidate              (salida automática, nunca canónica)
human_confirmed_observation    (única vía a dato canónico)
```

Estados de observación:

```text
OBSERVED_SOURCE   dato de fuente estructurada (CNMV/FIRDS/GLEIF)
CANDIDATE         propuesta automática pendiente de revisión
CONFIRMED         confirmado por revisor con evidencia citada
REJECTED          descartado por revisor (con motivo)
CONFLICT          fuentes/claims incompatibles -> resolución humana
MISSING           campo buscado, no encontrado (hecho negativo útil)
```

## 4. Métricas preregistradas de P0

```text
time_to_review_per_instrument
candidate_accept_rate / candidate_reject_rate
fields_confirmed_per_minute
evidence_navigation_accuracy      (¿la evidencia mostrada es la correcta?)
review_corrections
inter_reviewer_agreement
```

Comparación de referencia obligatoria:

```text
manual PDF workflow  vs  Emisiones ES evidence-assisted workflow
```

Criterio de valor: si una emisión compleja exige ~15 min de lectura manual y
el workflow asistido permite revisión rigurosa en ~3-5 min, el producto
existe aunque nunca haya extracción autónoma total. Umbrales concretos se
fijan en el protocolo de medición de P0 antes de ejecutarlo.

## 5. Prioridad de construcción

```text
1. Vista por ISIN/emisión
2. Grafo documental: base -> supplement -> final terms -> admission
3. Campos estructurados de fuentes (CNMV/FIRDS)
4. Candidate terms con evidencia resaltada (page+bbox)
5. Confirm / Reject / Conflict
6. Historial y provenance por decisión
7. Export JSON/CSV/Parquet de datos confirmados
8. CLI / API de consulta
9. MCP — último, como interfaz del dataset ya validado
```

## 6. Anti-objetivos de P0

```text
NO G3 ni nueva ronda de extracción automática
NO nuevos backends / parsers / embeddings para extracción contractual
NO promoción de machine_candidate a canónico sin CONFIRM humano
NO API pública/MCP antes del reviewer workflow
```

## 7. Condición de cierre de P0

P0 cierra cuando exista evidencia medida de la comparación del §4. Si el
workflow asistido no mejora materialmente la revisión manual, el proyecto
queda como dataset/reference-layer OSS sin capa de revisión — resultado
igualmente válido y defendible.
