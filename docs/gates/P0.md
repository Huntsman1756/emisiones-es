Emisiones ES deja de ser un proyecto de *document extraction*. Es:

> **Securities reference-data & document intelligence para el mercado español, con linkage auditable y extracción human-in-the-loop basada en evidencia.**

El proyecto pasa de *research* a *pre-MVP listo para productización*. No hay G3. Los resultados negativos se conservan: el workflow human-in-the-loop no es una concesión arbitraria, es una frontera determinada experimentalmente.

## 1. Hipótesis de producto

> Emisiones ES permite a un profesional revisar y confirmar los términos de una emisión de forma materialmente más rápida que el workflow manual sobre CNMV/PDF, sin degradar exactitud, completitud ni auditabilidad.

Unidad de producto:

```text
instrument → document graph → machine candidates → exact evidence
           → human confirm/reject → canonical reviewed observations
```

**No existe promoción automática de `CANDIDATE` a `CONFIRMED`.** `machine_candidate` y `human_confirmed_observation` son capas separadas; la capa automática nunca contamina el security master. Estados: `OBSERVED_SOURCE / CANDIDATE / CONFIRMED / REJECTED / CONFLICT / MISSING`.

## 2. Protocolo (contrato completo en `p0/manifests/protocol.json`)

- **Muestra**: 30 emisiones **nuevas** — admisiones CNMV 2019-2020, período nunca recolectado → solape 0 con G0/G1/G2 por record-key/URL/SHA256 (verificado contra 483+728 claves usadas). Los 97 docs G1 sirven para desarrollar la UI, **no** para medir el producto.
- **Estratos** (features pre-review, regla congelada): LOW 10 / MEDIUM 10 / HIGH 10. 16 emisores, máx 30% un emisor, todo `FAMILY_COLD`.
- **Revisores**: 2, con experiencia financiera, sin conocer outputs/gold del otro. Fallback explícito si no hay segundo revisor: **P0-pilot de un revisor, no concluyente**, para calibrar interfaz — el gate oficial espera al segundo.
- **Diseño cruzado**: cada caso 1×MANUAL + 1×ASSISTED por revisores distintos (15/15), seed congelada, orden de casos aleatorio independiente por revisor. Warm-up: 4 casos fuera del holdout.
- **Timing**: `ACTIVE_REVIEW_TIME` automático apertura→submit; interrupción >5 min → `INVALID_TIMING` (repetible solo sin haber visto gold/output ajeno; primer intento se conserva).

## 3. Gates

```text
TIME      median(time_ratio) ≤ 0.60  (≥40% reducción)
          ≥70% de 30 casos más rápidos en ASSISTED
          upper 95% CI bootstrap de median ratio ≤ 0.80
QUALITY   assisted confirmed-precision ≥ 99%
          precision_assisted ≥ precision_manual − 0.01
          recall_assisted ≥ recall_manual − 0.05
SAFETY    CRITICAL_ERROR assisted = 0
          unsupported CONFIRMED = 0
          provenance válida = 100% en CONFIRMED assisted
EVIDENCE  navegación correcta ≥ 98%; 0 links a documento equivocado
```

Gold: post-hoc desde documentos fuente/metadata oficial/graph evidence — nunca el output automático como autoridad; versionado truth-v1/v2 + semantic diff como en G0/G1.

**PASS** requiere todos los hard gates. **FAIL**: más rápido pero menos seguro · seguro pero ahorro mediano <40% · velocidad por menor completitud. **INCONCLUSIVE** solo si <24/30 paired timings válidos o problema externo — nunca por rendimiento insuficiente. Sin `PASS WITH CAVEATS`.

## 5. Anti-objetivos (congelados)

- No usar docs P0 para modificar candidates, UI por layout ni graph logic.
- No sustituir casos por rendimiento de los candidates.
- No API pública, MCP ni chatbot antes del workflow de revisión.
- No promoción automática candidate→canónico, nunca.
- Umbrales no cambian entre fases P0-B…P0-F.
- Los diagnósticos por subgrupo (strata, family, tipo, reviewer) no cambian el verdict.
